# 未定义行为（UB）—— 为什么 `i++ + ++i` 没有答案

> 2026-10-30 从 19_operator_demo4/2.c 搬出来重写的。
> 原来那段是写在代码注释里的，跟一堆被注释掉的 main 混在一起，
> 想复习的时候根本翻不到。现在单独拎出来成一篇。

---

## 起因：一道让我纠结过的题

```c
int i = 10;
int j = 5;
int k = i++ + ++i - --j - i--;
printf("%d\n", k);
```

网上流传的说法是：

> Windows 先算前缀再算后缀 → 得 7；Mac 从左到右 → 得 6。

**这个说法不准确，而且会把人带偏。** 我当时记过这个结论，后来发现是错的。

---

## 真相

上面那个表达式里，`i` 被改了**三次**（`i++`、`++i`、`i--`），
而这三次修改之间没有任何 **序列点（sequence point）** 隔开。

这在 C 标准里叫 **未定义行为（Undefined Behavior，简称 UB）**。

UB 不是"每个平台的计算结果不一样"这么温和的事。它的意思是：

> **C 标准对这种写法的结果不作任何保证。**

所以：

- 换编译器，结果可能变
- 换优化等级（Debug / Release），结果可能变
- 甚至同一次运行里，结果都可能变
- 也可能直接崩溃

**7 和 6 都不能当结论记。** 两者都只是某一次某个编译器碰巧给出的数字。

---

## 为什么标准要这么规定

因为它给编译器留了优化的余地。

编译器看到 `i++ + ++i`，理论上可以按任意顺序处理这些副作用，
挑最快的那种。标准要是规定死了顺序，编译器就没得 optimizations 了。

代价是：**这种写法的结果由编译器说了算，不关你的事。**

---

## 判据（背这三条就够）

> **1. 一个表达式里，别对同一个变量改两次以上。**
>    `i++ + ++i`、`a = a++`、`printf("%d", x++, x)` 全是坑。
>
> **2. 看到"不同平台结果不一样"，先怀疑 UB，别急着背具体数字。**
>    真正的跨平台差异（比如 `int` 是几个字节）是可预期的；
>    UB 是不可预期的。两者的区别在于能不能写进文档。
>
> **3. 想看清自增的先后，就拆成多条语句写。**
>    拆开之后每一步都在求值顺序确定的地方，结果立刻变确定。

---

## 正确写法：拆成多句

```c
int a = 10;
int b = a++;   // b = 10，a = 11（先用后加）
int c = ++a;   // a = 12，c = 12（先加后用）
printf("a=%d b=%d c=%d\n", a, b, c);
```

每一步单独成句，句与句之间有语句边界（这就是序列点），
所以每次运行结果都一样，换什么编译器都一样。

干净的前后缀演示在 **`17_increment_operator`** 项目里，
能直接 F5 跑，看见的就是确定的输出。

---

## 同一类的坑（都别写）

| 写法 | 问题 |
|---|---|
| `i++ + ++i` | 同一个表达式里改了 i 两次 |
| `a = a++` | 等号左边也在改 a，右边也在改 a |
| `printf("%d", x++, x)` | 一个读、一个改，顺序不保证 |
| `arr[i] = i++` | i 被改的同时还被用来当下标 |
| `f(i++) + g(i++)` | 两个函数调用之间顺序不保证 |

**共同点：同一个变量，在同一个表达式里既被读又被改，或者被改了不止一次。**

---

## 一句记牢

> **UB 没有答案，只有后果。**
> 遇到拿不准的表达式，别猜它在你机器上等于几，
> 拆成几句话写 —— 拆开了，它就是确定的。
